# Gateway load test

_Generated by `python -m eval.load_test`. Providers are MOCKED (instant canned answers), so these numbers are RouteWise's own overhead, not LLM latency._

* Two scenarios of 45 s each: 1 user (no contention) and 10 concurrent users. Single uvicorn worker on a laptop CPU, Redis off, semantic cache on, SQLite request logs.
* Mix per user: 3x new questions (cache-miss path: embedding, FAISS, guards, verifier, router, mock LLM, logging) to 1x repeated questions (semantic-hit path).

## Reading it honestly

* The **1-user** rows are the real per-request cost of RouteWise's pipeline on CPU. It is dominated by the two transformer models (bi-encoder embedding + cross-encoder verifier).
* Under concurrency the server-side times grow too: they are wall-clock times that include waiting for the shared CPU (one worker, model inference in a thread pool, torch threads competing). Throughput, not per-request work, is the limit; more workers, batching across requests, or a GPU would raise it.
* Relative to a real LLM call (seconds on the free tiers used in this project) the single-user overhead is small, and a cache hit replaces the LLM call entirely.
